# Release and signing runbook

Owner-only procedure for `DAT-005` (stable signing identity) and `DAT-008`
(release discipline). The agent never generates, reads, stores, or asks for
signing keys or passwords. Nothing in this document is a secret; every value in
angle brackets is supplied by the owner.

## Why the signing identity is permanent

Android treats an APK as an update only when it has the same `applicationId`
and is signed by the same certificate as the installed app. A different
certificate forces every user to uninstall, which deletes local training data.
The `applicationId` can never change after the first public release. A lost key
is therefore a data-loss event for users, not an inconvenience.

Decisions recorded on 2026-10-28:

- `applicationId`: `com.imdanialrashidi.gymlog`. It is permanent from the first
  public release; the display name can change without touching it.
- License: MIT (see `LICENSE`); the About screen states `MIT`.

Owner decisions still open before the first release:

- public product name (the launcher label is still "Gym Log", a generic name
  with known collisions; changing the label does not change the identity);
- reference device for the performance run (`docs/perf/REFERENCE_DEVICE.md`).
  The owner has a recent Android phone; record its model and version there.

## 1. Create the keystore once, offline

Do this on a trusted offline machine or an air-gapped step. Never run it in a
prompt, in CI, or in a directory inside this repository.

```sh
mkdir -p ~/keys && chmod 700 ~/keys
keytool -genkeypair -v \
  -keystore ~/keys/gym-log-release.jks \
  -alias gym-log \
  -keyalg RSA -keysize 4096 -validity 10000
```

- Use a unique, high-entropy password generated by a password manager. Do not
  reuse any other password.
- The alias (`gym-log`) is not secret; the keystore and passwords are.
- Do not move or rewrite the keystore after this step. Back it up instead.
- Verify the public certificate fingerprint (safe to store publicly):

```sh
keytool -list -v -keystore ~/keys/gym-log-release.jks -alias gym-log \
  | sed -n 's/^[[:space:]]*SHA256: //p'
```

Normalize it to 64 lowercase hex characters. This is the value for
`ANDROID_CERT_SHA256` below. It is a fingerprint, not key material.

## 2. Create two independent backups and prove them

The keystore plus its passwords need **two independent backups**, not two
copies on the same disk.

1. **Backup A — encrypted password-manager attachment.** Attach the `.jks` to a
   secure note in the owner's password manager; store the store password, key
   password, alias, and certificate fingerprint in the same entry. Enable
   two-factor authentication on the account.
2. **Backup B — offline encrypted drive or printed recovery kit.** Copy the
   keystore and credentials to an encrypted USB drive kept in a different
   physical location (or a printed recovery kit in a safe). Do not use a cloud
   folder that syncs the plaintext file.
3. **Prove both backups now.** Copy each backup to a scratch directory outside
   the repository and list the alias with the backed-up password:

   ```sh
   keytool -list -keystore /path/to/restored-copy.jks -alias gym-log
   ```

   Confirm the alias and fingerprint match the original. Delete the scratch
   copy afterward. A backup that has never been restored is not a backup.
4. Re-test one backup at least annually and after any password-manager change.
5. Never commit the keystore, a base64 copy, `key.properties`, or passwords to
   Git. `.gitignore` covers the common filenames, but the rule is the control.

## 3. Store CI secrets and the public fingerprint

Repository settings (owner, once):

```sh
# Prompted interactively; do not put passwords in shell history or argv.
gh secret set ANDROID_KEYSTORE_BASE64 --repo <owner>/<repo>
gh secret set ANDROID_KEYSTORE_PASSWORD --repo <owner>/<repo>
gh secret set ANDROID_KEY_ALIAS --repo <owner>/<repo>
gh secret set ANDROID_KEY_PASSWORD --repo <owner>/<repo>

# Public certificate fingerprint, not a secret.
gh variable set ANDROID_CERT_SHA256 --repo <owner>/<repo> \
  --body "<64 lowercase hex characters>"
```

For the keystore secret, base64-encode the file without line wrapping and feed
it only to the `gh` prompt or stdin; never paste it into a prompt for an agent
and never commit it:

```sh
base64 -w0 ~/keys/gym-log-release.jks | gh secret set ANDROID_KEYSTORE_BASE64 \
  --repo <owner>/<repo>
```

Repository settings (owner, once):

- Protect `v*` tags against updates and deletion so a released tag cannot be
  moved.
- Add required reviewers to the `release` environment used by the workflow.
- Keep the `main` branch protected; the workflow refuses a tag whose commit is
  not an ancestor of `origin/main`.

The release workflow:

- passes signing values to Gradle only through environment variables;
- never prints a secret or passes a password on a command line;
- decodes the keystore into `$RUNNER_TEMP` with mode `600` and deletes it after
  the build (`trap`);
- uses no debug-key fallback: `android/app/build.gradle.kts` creates the release
  signing config only from `GYM_LOG_*` environment values and refuses release
  tasks when they are missing;
- refuses a keystore located inside the repository.

## 4. Local signed build (optional, owner machine)

Instead of CI, the owner may sign locally using short-lived environment values
from the password manager. Do not create `android/key.properties`.

```sh
export GYM_LOG_KEYSTORE_PATH="$HOME/keys/gym-log-release.jks"
export GYM_LOG_KEYSTORE_PASSWORD='<from password manager>'
export GYM_LOG_KEY_ALIAS='gym-log'
export GYM_LOG_KEY_PASSWORD='<from password manager>'
flutter build apk --release
```

The same Gradle guards run: applicationId, manifest, and signing material.
Clear the variables and shell history after the build.

## 5. Release discipline in the repository

`CHANGELOG.md` is the release source of truth. Every versioned entry needs:

```md
## [1.2.3] - 2026-10-25

Build: 7
Schema: none
```

- `Build:` is the Android version code and must increase for every release.
  `tool/guards/check_changelog.dart` enforces monotonic values and that the
  newest entry matches `pubspec.yaml`'s `version: X.Y.Z+N`.
- `Schema:` is `none` when the persisted document schema did not change; use
  the new version/reason otherwise (for example `v3 (added columns)`). The
  workflow marks schema changes as **pre-release** automatically.
- Add a new export fixture under `test/fixtures/export/v<version>.json` for
  every release; never edit an older fixture (see
  [EXPORT_FORMAT.md](EXPORT_FORMAT.md)).
- Release notes in plain English and Persian are an owner step. The workflow
  seeds the GitHub notes from the CHANGELOG entry; edit them to add the Persian
  section before announcing.

## 6. Release workflow

`.github/workflows/release.yml` runs only on a pushed tag matching
`vX.Y.Z`. The owner creates the tag; agents never tag, push, or release.

Order:

1. **Preflight (no secrets):** the tagged commit is on `main`, the tag matches
   `pubspec.yaml`, CHANGELOG validates, and Gradle's
   `verifyReleaseApplicationId` refuses the placeholder.
2. **Verification gate (no secrets):** runs `scripts/verify.sh`, including the
   tests, benchmarks, signing-material guard, and manifest guard.
3. **Secret presence:** fails with the missing secret names (never values)
   before the signed release build.
4. **Signed build:** signed release APK with secrets from the environment.
5. **Certificate check:** compares the APK signer's SHA-256 with
   `ANDROID_CERT_SHA256`; a wrong-but-valid key stops the release.
6. **Checksums:** produces `gym-log-vX.Y.Z.apk` and
   `gym-log-vX.Y.Z.apk.sha256`, then verifies the checksum immediately.
7. **GitHub release:** uploads both files, uses the CHANGELOG notes, and adds
   `--prerelease` when `Schema:` is not `none`.

Before tagging, run `bash scripts/verify.sh` and complete the checklist below.

## 7. Upgrade drill (before every release)

Run on a real device, not an emulator.

1. Install the previous public APK: `adb install -r previous.apk`.
2. Create realistic data: a program with days/items, a finished session with
   notes and a few sets, an exercise photo, settings changes, and an export.
3. Record the export's SHA-256.
4. Install the new APK over it: `adb install -r gym-log-v<new>.apk`.
5. Verify programs, history, session detail, charts, PRs, settings, and photos
   are intact. Re-export and compare the JSON structure; confirm no data loss.
6. Import the older export into the new app (Merge and Replace as appropriate)
   and confirm validation and previews behave.
7. Record device, Android version, previous/new version codes, date, and result
   in the release checklist. `A14` stays `UNPROVEN` until this passes.

The first public release has no previous signed APK and no update path: the
permanent `applicationId` starts a new install identity. Record a fresh-install
round-trip instead (create data, export, uninstall, reinstall, import) and start
the update drill at the next release, using the first release as its baseline.

## 8. Failure paths

| Failure | Detected by | Required response |
|---|---|---|
| Missing secret/variable | Workflow "Require signing secrets"; Gradle `verifyReleaseSigning` | Restore the secret from Backup A/B; never substitute a debug key. Re-run the failed tag workflow. |
| Wrong certificate (valid key, wrong identity) | `tool/release/verify_apk_certificate.sh` before upload | Stop. Do not publish. Restore the original keystore from both backups and confirm its fingerprint; changing `applicationId` is not a fix. |
| Checksum mismatch | `sha256sum -c` in `package_apk.sh` / user verification | Do not publish or install. Re-run the pipeline; if it recurs, treat the artifact/runner as suspect. Never upload a checksum you did not verify. |
| Keystore path inside repo | Gradle `verifyReleaseSigning` | Move the key outside the repository and rotate it out of any backup that leaked. Git history must never contain it. |
| Keystore empty after base64 decode | Workflow build step (`-s` check) | Recreate the secret from a proven backup; verify locally with `keytool -list`. |
| Lost key or password | Upgrade drill / install failure for users | There is no recovery for installed users: they must export, uninstall, and reinstall. This is why two independent backups and the restore proof are mandatory. |
| Placeholder `applicationId` | Gradle `verifyReleaseApplicationId` (also in preflight) | Choose the permanent name and update `namespace`/`applicationId` together; never release under `com.example`. |
| Schema changed but release not pre-release | CHANGELOG `Schema:` + workflow `--prerelease` | Fix the CHANGELOG entry, not the workflow. Promote only after the upgrade drill and friend testing. |

## 9. Release checklist (Section 37.4)

- [ ] `bash scripts/verify.sh` passed locally and in CI.
- [ ] New export fixture added; older fixtures untouched.
- [ ] Upgrade drill passed on a real device (Section 7).
- [ ] Performance budgets verified in profile mode; device rows in
      `docs/perf/RESULTS.md` updated.
- [ ] Manifest checked: no `INTERNET`, backup disabled
      (`./gradlew :app:verifyReleaseManifest`).
- [ ] Signed with the permanent key; certificate fingerprint matches
      `ANDROID_CERT_SHA256`; checksums generated and verified.
- [ ] `CHANGELOG.md` entry has the correct version, increasing `Build:`, and an
      explicit `Schema:`.
- [ ] Release notes written in plain English and Persian.
- [ ] Marked pre-release first when the schema changed; promoted only after
      friends confirm.
- [ ] `applicationId`, license, project name, and reference device decided by
      the owner.
- [ ] Tag protection and the `release` environment's required reviewers are
      configured.
